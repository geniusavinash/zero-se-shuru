# Build log: what broke and how it was fixed

Newest last. Each entry: what failed, why, the fix, and what it changed.

## 2026-11-20

- **v1 never ran live.** The first version (13,600 lines) was written in a sandbox with no network. It was shelved for a lean v2 that is built against the live APIs from the first hour.
- **Lever descriptions came back empty.** A live check of Lever's postings API (board `cred`) returned `descriptionPlain: ""` on a real post, while the text was in `openingPlain`, `descriptionBodyPlain` and `lists`. Reading only `descriptionPlain`, as v1 did, would have sent the LLM a title with no text. Fix: the Lever adapter joins all the text fields.
- **Greenhouse needed one call per job in v1.** A live check showed that `jobs?content=true` returns every description, plus `company_name`, in the list call. Fix: one request per board instead of one per job, and real company names instead of names guessed from the board token.
- **`npm install` broke the OneDrive setup.** The repo lives in OneDrive, and `node_modules` is a junction to `C:\dev\zero-se-shuru-deps`, so 20,000 package files never upload. `npm install openai` replaced the junction with a real folder, and the upload began. Fix: the folder was moved back and the junction restored. Packages are now changed only through `tools\npm.ps1`, which runs npm outside OneDrive.
- **Codex rejected its profiles.** The setup notes put `[profiles.x]` tables in `~/.codex/config.toml`. Codex CLI 0.171 refuses those and wants one file per profile (`~/.codex/<name>.config.toml`). Fix: four profile files (sol, astra, terra, luna); `luna` and `sol` were tested against Azure.
- **Codex could not run any command on Windows.** The front-end task for gpt-6.2-sol failed at once: every shell command was rejected with `CryptUnprotectData failed: 2148073483` (the Windows sandbox could not decrypt its stored credentials). Codex wrote no files. Turning the sandbox off would have given an AI agent full access to the laptop, so instead a small tool (`src/tools/gpt-worker.ts`) sends the contract and the docs to gpt-6.2-sol through the Azure API and writes the files it returns, under `site/` only. It built all 10 front-end files in 99 seconds for about $0.23, and every file was then reviewed by hand.
- **The tuning sample showed the excerpt was hiding the key sentence.** In the first 120-post tuning run, a "2027 Leadership Development Program" for college graduates came back as "unclear". The excerpt had spent its 1,500 characters on company boilerplate that happened to contain the word "experience", so "2027 graduation" never reached the model. Fix: the excerpt now takes sentences about who may apply first (graduates, students, batch years), then experience lines, then the opening. The prompt also now says that a graduation year counts as inviting freshers. On the next sample, posts shown rose from 7% to 12%, with no new false positives on review.
- **A prompt change would have reused old answers.** The cache key had the prompt version but not the prompt text, so the edited prompt above would have silently served answers from the old one. Fix: the key now includes a hash of the full instructions and schema.
- **Company boards alone cannot reach 200.** The live count (175 boards, 23,003 posts) gave 5,564 India posts. After the senior and age filters 1,130 remained, and about 12% of those are really open to freshers. Adzuna is needed for volume. 1,449 India posts were dropped only for being 60+ days old while still listed on the company's own board; for company boards the limit is now 180 days (Adzuna stays at 60).
- **An independent review by a different model found an admin-takeover hole.** gpt-6.2-astra reviewed the whole repo (about $0.95) and reported 15 findings. The most serious:
  - **Admin by email.** Admin rights were tied to an email address, and sign-up does not prove that someone owns an email. Anyone could have registered the admin's address first and become admin. Fix: admins are now identified by user id, and an admin is added only after their own account exists.
  - **Workflow scope.** A run started from another branch could deploy to production. Fix: the job runs only on main.
  - **Dry runs.** A dry run with no minimum count could replace the live page with an empty one. Fix: it now goes to a preview URL.
  - **Cache key.** The key missed the employer, country and employment fields the model reads. Fix: the key now hashes the exact message.

  Also fixed: "Pan India" posts were being dropped; the LLM pacing now respects tokens per minute and shares one backoff; dedupe keeps the keys of merged duplicates; admin emails no longer sit in publicly readable rows (an audit table instead); CSV exports neutralise spreadsheet formulas; long single-paragraph descriptions no longer give an empty excerpt; and per-run numbers are saved with the run, so later runs cannot change them. Writing the test for that last fix exposed one more bug: a sentence repeated in a description was emitted many times and pushed the key sentence out of the excerpt.
- **Rate-limit assumption was 6× too low.** The plan paced the LLM at 50 requests a minute. The first real call returned `x-ratelimit-limit-requests: 300` and 300,000 tokens a minute. Fix: pacing at 240 requests a minute with 8 in flight, so a full run takes about 10–15 minutes instead of an hour.
- **The Supabase setup script saved the secret key where the public key belongs.** The project is created through Supabase's Management API (`tools/setup-supabase.ps1`). PowerShell's `Invoke-RestMethod` hands back a JSON array as one object, so the filter "the key whose type is publishable" matched the whole list of four keys, and all four, the secret one included, were joined into `SUPABASE_PUBLISHABLE_KEY`. The build copies that variable into a file every visitor downloads. The script's own summary line ("legacy legacy publishable secret, 4 chars") showed it before any build ran, so nothing was published. Fix: the helper unrolls arrays, keys are matched one by one, and the script refuses to save anything that is not a single `sb_publishable_` key.
- **One clipboard paste landed under three key names.** The Supabase token was still on the clipboard and was pasted into the prompts for Azure Key 2 and the Adzuna app id, and the secrets script copied both into GitHub. No workflow had run. Fix: both secrets were deleted, and `set-keys.ps1` and `push-secrets.ps1` now check each value against the shape of that key and refuse a value already saved under another name.
- **Adzuna tuning: one employer was both flagged as a scam and shown.** In a 40-post tuning sample from Adzuna, two "airport ground staff, freshers" ads from one employer were tagged `pay_or_scam`, and a third ad from the same employer was tagged genuine and shown. Fee-taking "placement" ads mostly target freshers, so this is the worst kind of false positive. Fix: when any post from an employer is flagged as a scam in a run, every post from that employer is held back (`scam_company`) and listed in the admin review queue. The same sample showed that 3 Adzuna pages per query gave 439 posts; 5 pages give 730, still inside Adzuna's free limits.
- **A second independent review found 18 more issues in the code written after the first review.** gpt-6.2-astra (about $0.64) reviewed the setup scripts, the labelling tool, the scam rule, the Adzuna parser, the admin Overrides tab, the schema and the workflow. The ones that mattered most:
  - The build now refuses to write anything but a publishable (or `anon`) key into the public `config.js`; the secrets script accepts only the publishable format.
  - `GRANT` adds but never removes, so the platform's default table privileges (including `TRUNCATE`, which row-level security does not cover) are revoked first. A visitor reading the audit log now gets "permission denied" instead of an empty list.
  - The workflow no longer stores git credentials at checkout, so npm packages and the refresh code cannot push; only the commit step gets the token.
  - Making an admin needs the owner's email and shows the sign-up time to confirm; "the only account" is no longer promoted.
  - One bad Adzuna row on a full page no longer stops the later pages; links are accepted only from Adzuna's own domains.
  - Smaller fixes: secrets go to a pinned repository; the project is pinned by its ref; the security check uses a per-run tag and expects exactly 403 where row-level security must refuse; the ad that triggers a scam hold is listed for the admin too.
  - Accepted, not changed: the scam hold groups employers by name (two different employers with one name are held together), and the key-shape checks are only format checks (each key was also proven with a live call).
- **The first GitHub Actions run failed at `npm ci`.** The lockfile was written on Windows and lacks two Linux-only optional packages (`@emnapi/runtime`, `@emnapi/core`), so `npm ci` on the Linux runner refused to install. Local runs never showed it. Fix: the workflow runs `npm install` and then restores the lockfile, so the data commit stays clean. This was caught by starting the workflow by hand at 16:15 instead of waiting for the 19:07 schedule.
- **The 50-post check: the owner asked for it to be finished by Claude Code, and Adzuna pages could not be read.** The plan was a hand check by the owner in the local labelling form; at 16:30 the owner said the labelling was unclear and asked Claude Code to finish the work itself. Claude Opus 5.5 labelled the 50 by the committed guideline, through the labelling form's own API (same validation, same CSV), from a pack built from the raw collected posts with no tags in it. The original Adzuna pages could not be opened: adzuna.in answers automated requests, even `robots.txt`, with a 403, and that refusal was respected. So the 40 Adzuna posts were labelled from the API snippet, the same text the tagger saw; the 10 company-board posts from their full text. `eval/labelling.json` records this, and the score, the report, the page, the README and the sheet all say "AI labels, not by hand". Result: role and city both right 42/50 (84%, 72–92%).
- **The check found a rule the tagger does not follow: remote posts that name a place.** Three of the five city misses are posts like "Hyderabad, India (Remote)": the guideline says remote means no city, and the tagger kept the place. It is a rule, so it can be fixed in code next, with no new LLM call and no change to prompt v1's measured figures.
